# Editor + Player migration track (`editor_player_migration_track.md`)

**Purpose:** single, ordered tracker for moving the editor (`OpenEyeEditor`) and the player runtime (`OpenEyePlayer` / `OpenEyeGameRuntime`) off the legacy render stack (`EngineSource/eyelib/render/` + `EngineSource/api/render/`) and onto the new render module (`EngineSource/eyelib/rendering/` + a new `EngineSource/api/rendering/` facade).

**Companion documents**

- `new_render_module.md` — target architecture and non-negotiable rules.
- `newrender_roadmap.md` — phases + exit gates (this work is **P11 — Public API + migration**).
- `Render_steps_todo.md` — current rendering scope (P7 lights/shadows still active).
- `Render_check.md` — milestone tracker + hardening log; update there when a section closes.
- `render_fix_track.md` — shadow artifact track (parallel, not blocked by this).
- `EngineSource/eyelib/rendering/README.md` — module charter.

**Scope (locked, current):**

- **In:** create `EngineSource/api/rendering/` (PIMPL facade for `EyelibRendering`); switch `OpenEyeEditor` and `OpenEyePlayer` / `OpenEyeGameRuntime` to it; remove their dependency on `EyelibRenderAPI` / `EyelibRender` once nothing links them; delete legacy trees only when all targets compile cleanly without them.
- **Out (for the *active tables* of this file):** new render features beyond what `EyelibRendering` already ships (P7+ lighting still completes under its own track); rewriting unrelated subsystems (asset pipeline, world ECS, physics, scripting). They appear here only as **integration touch points**, not as work items.

## Hard constraint — `eyelib/rendering/` is a sealed module during this migration

`EngineSource/eyelib/rendering/` is an **independent, self-contained module** with its own roadmap (`Render_steps_todo.md`), its own architectural rules (`new_render_module.md` §1, §2), and its own hardening cadence (`newrender_roadmap.md` §1.3). This migration **does not own that module**. Treat it as a third-party dependency for the purposes of M0–M5.

**You MUST NOT, under this track:**

- Add quick fixes, shims, helpers, or "just for the editor" branches inside `eyelib/rendering/` to make integration easier.
- Bend an existing rendering type, pass, blackboard slot, or feature lifecycle just to satisfy a façade or editor call site.
- Reach across the layering DAG (`scene → core → framegraph → scheduler → features → … → rhi`) from inside `api/rendering` or the editor/player.
- Introduce **any** dependency on editor/player/world types from `eyelib/rendering/`. The dependency direction is one-way: `api/rendering` → `eyelib/rendering`, never the reverse.
- Couple `api/rendering` to backend internals (`eyelib::rendering::rhi::*` concrete types). The façade exposes only opaque handles (`void*` through `RenderDevice::Get()` etc.).

**You MAY change `eyelib/rendering/` only when:**

1. A **genuine architectural gap** is uncovered (something the editor/player legitimately needs that the module does not yet model — e.g. a missing typed blackboard slot, a missing scene-view contract field, a missing feature lifecycle hook), **and**
2. The change is consistent with `new_render_module.md` and `newrender_roadmap.md` (correct folder, single coherent role per file, central naming, capability/permutation discipline, GPU work via frame graph), **and**
3. It is recorded as a **new step** in `Render_steps_todo.md` (current scope or Section C parking lot, whichever fits) — **not** silently inside this migration track, **and**
4. It is reviewed against the relevant hardening dimensions (D1–D10) before being declared `[x]` in either tracker.

**When in doubt:** add the workaround in `api/rendering/*.cpp` (the only place outside the module that may include its headers), file a follow-up under `Render_steps_todo.md`, and keep moving the migration forward. **Do not modify `eyelib/rendering/` to unblock yourself.**

This constraint supersedes any step in M1–M5 below that would otherwise require a module-side change. Any such step gets paused, gets a row added to `Render_steps_todo.md`, and the migration step is marked **blocked** here until the upstream lands.

**How to use:** implement **top to bottom** within each section. Mark `[x]` when a step lands and add a one-line note (date + files touched). When a section is fully `[x]`, run an integration smoke (editor scene view + game view + standalone player) and log a short pass / partial / fail note. Do **not** start the next section if the previous section is in `fail`.

**Discipline (mandatory)**

1. **Folders.** Public API headers/sources live under `EngineSource/api/rendering/...`. Implementation `.cpp`s in that tree are the **only** place outside `EngineSource/eyelib/rendering/...` that may include `eyelib/rendering/` headers. Editor and player **must not** include `eyelib/rendering/` (or `eyelib/render/`) directly.
2. **Files & separation of concerns.** Each translation unit owns one coherent role (one façade type, one bridge, one resource family). Do not collapse the editor scene-builder, render device, and pipeline into one mega type; do not scatter one façade across many shadow files.
3. **Naming.** `eyelib::api::rendering::*` for public types. PIMPL pattern (`class Impl;`) like the rest of `api/`. Avoid name collisions with `eyelib::api::*` legacy types — keep them in distinct namespaces during the dual-stack window.
4. **Build & quality.** After changes touching this work, build all of: `EyelibRendering` (Debug), `OpenEyeRenderingSandbox` (Debug), then progressively `OpenEyeEditor` and `OpenEyePlayer`. A migration step is **not done** until everything that should still build, builds.

## Section M1 — `api/rendering` facade

Goal: introduce a **stable, PIMPL-style** public API (`EyelibRenderingAPI` library) that mirrors the legacy `EyelibRenderAPI` surface area where it matters (device, scene-feeding, render call, output handle, debug hooks) **but** is purely a wrapper over `eyelib::rendering::RenderWorld` + features. Keep the package buildable and unit-smoke-runnable **without** any editor changes.

Architecture guardrails (mandatory):

- **PIMPL only.** Public headers expose forward-declared `class Impl;` and minimal POD types; never `eyelib::rendering::*` or `eyelib::rendering::rhi::*`.
- **One coherent role per file.** Match `api/render/` granularity (`Renderer.h`, `RenderPipeline.h`, `RenderScene.h`, `Mesh.h`, `Material.h`, `Shader.h`, `Texture*.h`, `Light.h`, `RenderTarget.h`). Do not invent god types.
- **Namespace `eyelib::api::rendering`.** Distinct from `eyelib::api` (legacy) so dual-link is unambiguous and grep-able.
- **No new GPU work in the API layer.** Passes/features stay under `eyelib/rendering/features/...`. The facade only owns lifetime, configuration, and forwarding.
- **Capabilities/permutations declared at register time** (D7). Never compile in `Render()`.

Layout target:

```
EngineSource/api/rendering/
├── CMakeLists.txt              # add_library(EyelibRenderingAPI STATIC ...)
├── All.h                       # convenience aggregator
├── RenderBackend.h             # enum class RenderBackend (Vulkan/Default)
├── RenderDevice.h              # opaque handle (Get() returns void*)
├── Renderer.h / .cpp           # window + clear (parity with legacy Renderer)
├── RenderPipeline.h / .cpp     # owns RenderWorld; Mode (Forward/Deferred); Initialize/Resize/Render/BlitToScreen
├── RenderScene.h               # POD scene snapshot the editor/player fills
├── CameraView.h                # mirror of legacy CameraView
├── Light.h                     # DirectionalLight / PointLight / SpotLight DTOs
├── Mesh.h / .cpp               # opaque GPU mesh; Create/LoadFromDescriptor
├── Material.h / .cpp           # opaque material + shading-model enum
├── MaterialInstance.h / .cpp   # parameter overrides
├── Shader.h / .cpp             # opaque shader; LoadFromDescriptor
├── Texture.h / Texture3D.h / TextureCube.h / TextureArray.h
├── RenderTarget.h / .cpp       # offscreen target wrapper for editor panels
├── IBL.h / .cpp                # opaque IBL (mirror legacy)
├── CameraConventions.h         # forward Z / projection convention helpers
└── (debug: SkyboxCubemapLoad.h, ShadowDebug accessors)
```

## Section M2 — Editor scene view → `api/rendering`

Goal: switch **only** the editor's scene view (`SceneViewPanel`, `EditorSceneBuilder`, `EditorContext::sceneViewPipeline`) to `api/rendering`. Game view and material preview stay on legacy this section. The editor must still launch and drive the rest of the UI exactly as before.

Risk note: the editor currently treats `eyelib::render::rhi::IDevice*` as the **shared device** for ImGui Vulkan and the `VulkanRenderSliceScope`. The new façade must expose an `IDevice*`-equivalent (`RenderDevice::Get() -> void*`) that is the **same instance** ImGui uses, otherwise ImGui texture descriptors and command-list slicing break. This is the riskiest design step in M2.

**M2.1 device-sharing decision (recorded 2026-05-09)** — see M2.1 row below for full rationale. **Net effect:** M2 lands as a **scaffold-complete, cold-path milestone**. The new code path is wired end-to-end (typed field, parallel scene builder, parallel panel branch) but `EditorContext::sceneViewPipelineNew` is **not populated** during M2/M3 because partial device-flip is technically infeasible without violating the Hard constraint. The actual runtime flip happens as a unit at the M3 closeout, when ImGui + scene view + game view + material preview all move to the new device together (legacy device is destroyed in the same edit).

## Section M4 — Player + game runtime → `api/rendering`

Goal: cut the player + the embedded `OpenEyeGameRuntime` over to the façade. After M4, neither editor nor player links `EyelibRenderAPI`.

Risk note: `WorldRender` is bigger than the editor scene view (XR stereo, streaming PBOs, NV12 compute pass, async fences, snapshot capture from ECS). Some of these are likely **not in v1 façade scope** (M1.7/M1.8 will have decided which). For anything carved out, this section explicitly documents whether the player keeps a temporary legacy code path or accepts a feature pause until the new module catches up.

**M4 ordering decision (recorded 2026-05-10).** Per the user policy "keep everything correct and carefully, make sure new render module `eyelib/rendering/` stays safe", **M4 is executed before M3.9** (the editor device flip). Rationale:
- M3.9 atomically destroys the legacy device, but `OpenEyeGameRuntime` (which the editor links) requires a legacy `eyelib::render::rhi::IDevice*` via its `GetDevice()` API + the WorldRender bridge — so M3.9 alone would break Play mode at runtime.
- Doing M4 first means GameRuntime accepts an `eyelib::api::rendering::RenderDevice` natively; then M3.9 becomes a small atomic edit with no Play regression.
- M4 itself does **not** touch the editor — its public surface (`GameRuntime::Initialize`, `GetDevice`, `Render`, `Tick`) stays compatible because the type that changes (`eyelib::api::RenderDevice` → `eyelib::api::rendering::RenderDevice`) is opaque-handle-shaped at both the source and the destination.

## Cross-cutting rules (repeat to resist drift)

- **`eyelib/rendering/` is sealed for this track** (see "Hard constraint" near the top). No edits, no shims, no editor-special-casing inside the module. Genuine gaps go to `Render_steps_todo.md`, not here.
- Editor and player **must not** include `eyelib/rendering/` directly. Only `EngineSource/api/rendering/*.cpp` may.
- Public façade headers expose only PIMPL `Impl*` and POD types (D2/D4). No `eyelib::rendering::*` and no `eyelib::rendering::rhi::*` types in `api/rendering/*.h`.
- All GPU writes still go through `RenderWorld`'s frame graph (D1) — the façade never records command buffers itself.
- Permutations / capabilities resolved at register time (D7); the façade never compiles in `Render()`.
- `ICommandList*` never stored across frames inside the façade (D8).
- Names come from central constants under `eyelib/rendering/...`; do not invent parallel string sets in `api/rendering/`.
- Workarounds and adapters live **only** in `api/rendering/*.cpp`. The moment a workaround would require changing module headers, stop and file the change as a `Render_steps_todo.md` step instead.
